# 用户提供的农业目标检测模型

来源为用户明确指定的项目根目录 `best.pt`，原文件不作修改。
SHA256：`fafc2bb3ce9ef66189436e0ad175bf07a8a0973d52cf6ece210f827798733be4`。

该文件包含 YOLO26m Detect 头和 38 个农业类别，约 2038 万参数。
模型类别 ID 取自权重内的 `names`；中文名称与用户提供的类别表逐一核对，详见 `class-mapping-review.json`。
类别表按数量排列，不是模型类别 ID 顺序。表中的“无叶片背景”未出现在权重类别中，因此不额外编造第 39 个检测类别。

`model.onnx` 为 FP32 CPU 推理工件，输入 `[1,3,640,640]`，输出 `[1,300,6]`。
输出为 YOLO26 端到端目标框 `xyxy, confidence, class_id`；使用 0.25 阈值，保留真实分数，不将独立目标分数归一化为分类概率。
接口返回的框经过 letterbox 逆变换，坐标基准为服务端保存的 EXIF 转正原图，归一化至 0–1。

## 版本兼容与验证

权重保存版本为 Ultralytics 8.4.37，导出环境为 8.4.183。旧存档不含新版 `_end2end` 字段；默认 PyTorch 加载会误入 one-to-many 分支并产生大量异常高分细框。
验证与导出必须在新加载的模型对象上、融合模型之前显式恢复 `head.end2end=True`，使用已训练的 one-to-one 分支；不能在错误融合后再修改开关。

已对五个本地技术样例（含一张非方形图）比较正确分支 PyTorch 与 ONNX 的类别、分数和原图框位置；结果见 `parity-report.json`。
这是导出数值与几何一致性验证，不是独立检测集精度评估。用户原始标注路径在本机不可用，尚不能确认训练框表示病斑边界；界面称其为“检测目标框”，不能计算病斑面积或声称具备追踪能力。
某些样例的模型类别与来源目录标签不一致，使用时仍需人工复核；未提供可核验的独立检测 mAP，也不沿用旧分类模型的 Top-1 或 F1。

发布时应同时携带 `manifest.json` 与 `model.onnx`，通过 SHA256 验证后启用。旧分类发布目录保留，可通过 `MODEL_MANIFEST` 切换；不覆盖其权重。

## 从源码仓库恢复模型

本次 GitHub 提交包含代码、类别映射、清单及验证报告，不上传用户提供的 `best.pt`、重复导出的 `best.onnx` 或运行产物 `model.onnx`。这些文件仍保留在本机和已部署服务器中；已有分类模型的 Git LFS 管理方式不变。

新克隆仓库后，需要单独取得已验证的检测工件，将 `model.onnx` 放在本目录、与 `manifest.json` 相邻。其 SHA256 必须为 `ff623c94555ade8c08a425caee3fe6fba5465ebc61ebd81ee502376bca8d4773`，再按 `backend/.env.example` 配置 `MODEL_MANIFEST`。没有该工件时，不能把清单中的验证状态当作推理服务已经就绪。
