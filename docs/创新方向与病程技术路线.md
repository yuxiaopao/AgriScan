# 第一部分 · 项目现状诊断

## 1.1 一句话结论

> **你把「实验室 Demo」做到了 90 分，把「田间产品」做到了 30 分。创新的钱全在中间那条缝里。**

## 1.2 六维现状表

| 维度 | 现状（含代码位置） | 真实评价 |
|---|---|---|
| **模型** | PlantVillage 38 类单标签分类，验证集 Top-1 **99.73%**、测试集 Top-1 **99.67%**、macro-F1 **99.56%**（`models/releases/plantvillage-yolo26m-906cf72f6bf0/test-report.json`，测试集 10,999 张） | 数字漂亮，但**是实验室数据**。`manifest.json` 的 `scope` 字段与 `models/README.md` 已诚实写明「田间泛化尚需独立验证」。这个诚实既是资产，也是最大的创新入口 |
| **推理** | ONNX Runtime CPU，`BoundedSemaphore(1)` 硬并发=1，单图串行（`backend/app/inference.py:89,99`） | 只能「拍一张看一张」，无法批量巡检，无队列、无 worker |

| **交互/品牌** | 小禾 IP 体系扎实：17 套作物主题色板（`cropThemes.ts`）、8 帧精灵动画（`Xiaohe.tsx` + `xiaohe.css`）、6 种状态、可拖拽可缩放可最大化的浮动助手（`FloatingAssistant.tsx` + `useFloatingPosition.ts`） | **这是你最强的差异化资产**，但目前只是「装饰 + 聊天窗」，尚未转化为生产力 |
| **形态** | 桌面浏览器应用；移动端仅为窄屏适配（`design/dashboard-mobile.png`） | 真实用户 95% 在**手机上、地里、弱网下** |

## 1.3 已经做对、必须保护的东西

在动手创新前，先明确哪些是资产、不能丢：

1. **工程纪律**：冻结测试集、质量门槛（`training/config.json` 的 `acceptance`）、可复现种子、LFS 权重版本化、`models/releases/<name>-<sha前12>` 按内容寻址发布 —— 这套纪律在同类项目中极少见。
2. **诚实边界**：不生成虚构结果、无模型时返回 `awaiting_model`、候选类别不重新归一化、置信度不当作患病概率。**这是品牌，不要为了「看起来更强」而破坏它。**
3. **风格统一的前端**：色板 token 化（`CropTheme.tsx` 注入 CSS 变量）、作物主题切换、动画降级（`prefers-reduced-motion`）。已具备设计系统雏形。
4. **安全与健壮性**：图片二次编码去元数据、DecompressionBomb 防护、上传路径剥离、JWT 注销列表、登录限频、DB lease 防并发重复请求。

4. **药方不溯源** —— 推荐的农药不挂登记证号，出问题无据可查；

# 第三部分 · 创新方向（五层 19 条）

## A. 模型与算法层（技术护城河，答辩最好讲）

### A1. 不确定性校准 + 拒识（Open-Set）—— **最推荐的第一刀**

- **问题**：38 类之外的新病、非叶片图、拍糊的图，都会被强行塞进 38 类并给出 0.9 的置信度。当前 `threshold = 0.70` 是拍脑袋定的，不是校准出来的。
- **做法**：
  1. **校准**：temperature scaling / isotonic regression → 输出 **ECE**、可靠性曲线（reliability diagram）、Brier score；
  2. **OOD 检测**：MSP / Energy / Mahalanobis 距离 → 三类输出：`已知病害` / `疑似未知问题（转人工）` / `图像不合格（重拍）`；
  3. **工作点选择**：阈值由「拒识率–准确率曲线」决定，而非固定 0.70。
- **指标**：ECE 从 ? → <0.03；OOD AUROC；覆盖率–准确率曲线。
- **成本**：低。**所有竞品全都没做**，且与你项目「诚实」的人格完全一致。

### A2. 从「分类」到「病斑分割 → 严重度分级」

- **问题**：README 已写明「不输出病斑位置框」。但农户真正关心的不是「什么病」，是「**要不要打药、会损失多少**」。
- **做法**：YOLO-seg / U-Net 分支（数据：PlantDoc + 少量自标 + SAM 半自动标注）→ 病斑面积占比 → **严重度 0–5 级**。
- **价值**：把你从「识图工具」变成「决策工具」，并为「病程」提供量化纵轴（见第六部分）。

### A3. 田间域适应（Domain Adaptation）—— 把 99.67% 变成可信的田间数字

- **不要**再刷 PlantVillage 的第 3 位小数。
- **做法**：跨域评测矩阵 `PlantVillage(源) → PlantDoc / FieldPlant(目标)`，外加自采 200 张手机田间图；手段包括域随机化增强、TTA、少样本微调、伪标签自训练。
- **产出**：一张「**实验室 vs 田间**」对比表。这是项目最硬的学术资产，也是最好的品牌素材（别人不敢放）。

### A4. 主动学习闭环（数据飞轮）

- **现状**：低置信度样本只提示「人工复核」，然后就没有然后了。
- **做法**：低置信度 / OOD / 用户标记「识别错了」→ 自动进标注队列 → 农技员复核 → 增量训练 → 版本化上线。
- **已有基础**：`models/releases/<name>-<sha前12>` 的按内容寻址发布机制、`training/deploy_model.py`、`.runtime/model-deployments` 回滚记录 —— **只差最后一段自动化**。

### A5. 端侧轻量化（弱网友好）

- **做法**：ONNX int8 量化（44MB → ~11MB）+ ONNX Runtime Web / TF.js 做浏览器端离线推理；结果异步同步。
- **价值**：地里没信号也能识别。农村场景是刚需，不是炫技。

## B. 数据与知识层（现在最空，收益最快）

### B1. 农技 RAG：把「小禾」从聊天机器人变成「有出处的专家」

- **现状**：`extensions.py:answer_for()` 零检索，直接把问题丢给 LLM。
- **做法**：文档解析（农技手册／地方植保站病虫情报／品种说明书）→ 向量库（pgvector / Milvus / Qdrant）→ **混合检索（BM25 + 向量）** → **强制引用**（每条结论挂来源）。
- **杀手级垂直知识库**：**中国农药登记数据**（登记证号、有效成分、安全间隔期、适用作物）→ 生成用药建议时**必须命中登记标签**，否则不出药名。
- **效果**：竞品硬编码药方，你出的是**可溯源的处方**。同时解决当前 prompt 里「不凭单张图片开具体农药」的无奈 —— 不是不给，是**给得有依据**。

### B2. 区域病虫情报（区域热力图）

- **做法**：匿名聚合检测结果 → 县/乡级病害热力 + 时序 → 「你周边 12km 内 7 天出现 8 例番茄晚疫病」。
- **数据结构天然支持**：已有 `crop`、`created_at`，只差**模糊化的地理位置**。
- **隐私技术点**：GeoHash 栅格化 + k-匿名（每组 ≥ k 个不同用户才出图）。

### B3. 环境耦合风险模型

- **做法**：气象 API（温度 / 湿度 / 叶面湿润时长 / 降雨）→ GDD、露时、病害侵染模型（如番茄晚疫病 Smith 周期）→ **地块级风险分** → 驱动 Agrio 式预警。
- **升级路径**：从「看图诊断」升级到「**算出来你会得什么病**」。

## C. 数据模型与架构层（工程硬骨头，但必须做）

### C1. 从「检测单点」到「病程时间线」★（详见第六部分）

- 给 `Detection` 增加 `subject_id` / `follow_up_seq` / `severity`，前端做**同一叶片复拍比对**：病斑严重度曲线、类别演化、干预事件标注、药效判定。
- **产品价值最高、改动却最小**：已有 `plot_id`、`created_at`、`note`、`candidates` 快照、模型 sha，只差「把点连成线」。

### C2. 多租户 + 角色重做

- **现状**：注册成员可读全部数据（`security.py:readable`），仅两级角色。
- **做法**：`workspace_id` + 行级隔离 + 角色（农场主 / 农技员 / 只读专家 / 外部顾问）+ 邀请制。
- **意义**：「农服公司带 50 个农户上平台」这类真实场景的入场券。

### C3. 推理服务化：队列 + 批处理 + 多模型路由

- **现状**：`BoundedSemaphore(1)`，一次只能跑一张。
- **做法**：任务队列（Redis + arq / RQ / Celery）+ 批处理（200 张一次上传）+ 模型注册表路由（按作物选模型）+ 推理耗时/失败率监控。
- **已有地基**：`docker-compose.yml` 已有 Redis；`cache.py` 已有缓存失效机制。

## D. 前端与交互层（你的强项，还能再拉开一档）

### D1. 拍摄前置质检（把 domain gap 掐死在源头）★

- **做法**：`getUserMedia` 实时预览 + 引导框（叶片占画面 60%+）+ 实时提示（模糊度 Laplacian 方差 / 过曝 / 反光 / 背景复杂度）+ 自动裁边 + 保留 EXIF（GPS、时间、设备）。
- **投入产出比最高**：不重训模型，田间准确率直接涨。

### D2. 小禾从「吉祥物」升级为「任务型 Agent」

- **现有资产**：17 套作物主题、8 帧动画、6 种状态、可拖拽助手窗。
- **做法**：赋予 tool use 能力 → 「查地块 → 建巡检计划 → 批量检测 → 生成防治处方（带登记引用）→ 创建 7 天后复检任务 → 导出可打印巡田报告」，每步结果**落库 + 可审计**。
- **示例**：「小禾，帮我看看 3 号棚这周有没有异常，没有就排个下周巡检。」

### D3. 语音 + 方言 + 大字模式

- **场景**：农户在棚里戴手套、手上带泥，不会打字。
- **做法**：ASR 输入 + TTS 播报 + 高对比大字模式。工程量不大，「给真实用户做的证据」很有力。

### D4. 移动优先重构 + 原生壳

- **现状**：单文件 `styles.css`（69KB）+ 桌面卡片布局。
- **做法**：抽设计 token（`cropThemes.ts` 已是雏形），移动优先重构拍摄流；Tauri 打包（README 已注明未做），弱网离线可用。

## E. 产品、商业与内容层

### E1. 重新定位人群

从「通用农业 SaaS」→ 收窄到「**农技员的巡田工具**」（B2B2C）。农技员一人服务 50 户，需要**批量、报告、可交付凭证** —— 正好是「病程时间线 + 处方溯源 + 可打印报告」三件套。

### E2. 商业模式

诊断免费 → 卖「**可信度报告 + 处方合规凭证**」给农服公司 / 合作社 / 农资店。Plantix 已证明（API + 区域洞察 + 精准投放）能赚钱，且国内没人做合规版。

### E3. 内容资产

把 `training/final-report.md` 那套「可复现训练 + 质量门槛 + 冻结测试集」的工程纪律，做成**公开的「模型卡 + 评测协议」**。在全民吹准确率的赛道里，**「敢公开田间掉多少」就是品牌**。

### E4. 数据合规前置

地块位置模糊化（GeoHash + k-匿名）、图片脱敏、模型卡 + 数据来源声明 —— B 端客户第一句就问这个。

| **① 技术护城河** | **A1 不确定性校准 + 拒识** ＋ **A3 跨域评测矩阵** | 成本最低、指标最硬、竞品全空白，与「诚实」的项目人格完全一致 | `calibration-report.json`（ECE / 可靠性曲线 / OOD AUROC）+ 一张「实验室 vs 田间」对比表 |

| **③ 想象力上限** | **B1 农技 RAG（带农药登记引用）** ＋ **D2 小禾 Agent 化** | 把小禾从装饰变成生产力；「有出处的处方」是别人抄不走的 | 问「番茄叶子这样该打什么」→ 回答带登记证号 + 安全间隔期 + 来源链接 |

## 4.2 明确不做的 5 件事

1. 别再刷 PlantVillage 的 99.6% → 99.9%，一分不值；
2. 别再往聊天窗里堆功能，要加就加**工具调用**；
3. 别做通用农业大平台，收窄到「农技员巡田」；
4. 别在没有田间验证前对外宣称「准确率 99%」；
5. 别先做多租户再做病程 —— **病程是价值，多租户是门槛**，顺序不要反。

# 第六部分 · 病程（Disease Course）专项

## 6.1 定义

**一句话**：同一个患病主体（一片叶、一株、一个棚）从第一次被发现异常，到治好、恶化或稳定，**这条随时间变化的轨迹**就是病程。

- 医学称「病程」（course of illness）：急性、慢性、迁延；
- 植保称「**病情发展过程**」，量化后即**病情指数曲线**（disease progress curve）；
- 核心不是「此刻是什么病」，而是「**它正在往哪个方向走、走得多快**」。

## 6.2 病程的标准分期

| 阶段 | 田间表现 | 系统可观察到的 |
|---|---|---|
| **潜伏期** | 肉眼不可见，但已侵染 | 只能靠环境模型推算（温度 / 露时），图片无能为力 |
| **初发期** | 零星 1–2 个病斑 | 首次 `attention`，置信度高、面积小 |
| **扩展期** | 病斑连片、日扩展明显 | 严重度逐次递增 |
| **高峰期** | 大面积坏死、落叶 | 严重度触顶 |
| **稳定/衰退期** | 病斑边缘干枯、停止扩展 | 严重度不再增加（药效或自然衰退） |

> **关键**：同一次拍照只能告诉你「在第几阶段」；**连续几次拍照才能告诉你「以多快的速度往下一阶段走」**。后者才是农户愿意付钱的信息。

## 6.3 当前系统的病程能力 = 0

代码层面的明确证据：

```python
# backend/app/db.py:42
class Detection(Base):
    id, name, crop, plot_id, status, result, confidence,
    created_at, image_url, is_demo, note
```

- 每次上传 = **一条全新的、彼此无关的行**。今天拍番茄叶片甲，三天后拍同一片叶子，系统里就是两行陌生人。
- `plot_id` 只到**地块**粒度 —— 只能说「3 号棚有 2 条记录」，说不出「这片叶子变好没有」。
- `detection_predictions` 存单次推理快照（候选 + 模型 sha），**不与上一次比对**。
- `plot_data()` 的 `health_score = healthy / completed`（`main.py:41-48`）是**聚合统计**，不是病程 —— 回答「这个棚整体怎么样」，不回答「这个病在恶化还是好转」。
- `RecordsPage` 是**列表 + 筛选**，本质是「档案柜」，不是「病历本」。

> **结论**：当前系统 = 一台**化验机**（出单次化验单），不是一份**病历**（记录病情演变）。

## 6.4 一份真正的病程需要 5 个要素

| 要素 | 含义 | 当前状态 |
|---|---|---|
| **1. 主体** | 同一片叶 / 同一株的**身份**，复拍能认回来 | ❌ 完全没有 |
| **2. 时间轴** | 每次采样的时刻（绝对时间 + 距上次天数） | ✅ 有 `created_at` |
| **3. 状态序列** | 类别 + **严重度** + 置信度 | ⚠️ 有类别 / 置信度，**没有严重度** |
| **4. 干预事件** | 哪天打了什么药、修了什么枝、控了什么湿 | ❌ `note` 是自由文本，不可结构化 |
| **5. 对照基线** | 健康参考 / 相邻植株 / 上次采样点 | ❌ 完全没有 |

缺 1、3、4、5 —— 所以当前**做不出任何一条病程**。

## 6.5 最小可行数据模型（不用重训模型）

```sql
-- 主体：一片叶子（或一株）的身份，跨次复拍保持不变
CREATE TABLE leaf_subjects (
  id            VARCHAR(32) PRIMARY KEY,
  plot_id       VARCHAR(32) REFERENCES plots(id),
  crop          VARCHAR(40) NOT NULL,
  tag           VARCHAR(60),         -- "3号棚-第4行-东侧-第2株-下部叶"
  first_seen_at DATETIME NOT NULL,
  closed_at     DATETIME,            -- 康复/清除后封存
  cover_url     VARCHAR(500)         -- 首张参考图，复拍时做相似度匹配
);

-- 采样点：每次检测挂到主体上，形成序列
ALTER TABLE detections ADD COLUMN subject_id   VARCHAR(32) REFERENCES leaf_subjects(id);
ALTER TABLE detections ADD COLUMN follow_up_seq INT;      -- 第几次复拍：1,2,3...
ALTER TABLE detections ADD COLUMN severity      TINYINT;  -- 0-5 级，见下

-- 干预事件：病程曲线上的竖线
CREATE TABLE interventions (
  id          VARCHAR(32) PRIMARY KEY,
  subject_id  VARCHAR(32) REFERENCES leaf_subjects(id),
  happened_at DATETIME NOT NULL,
  kind        VARCHAR(20),   -- 用药 / 修剪 / 控湿 / 隔离
  product     VARCHAR(120),  -- 药剂名（未来可挂登记证号）
  dose        VARCHAR(80),
  operator    VARCHAR(80)
);
```

**迁移兼容性**：采用与当年新增 `detection_predictions` 相同的策略 —— 新表 + 可空新列，`Base.metadata.create_all` 自动建表，兼容现有 SQLite / MySQL 数据，历史记录 `severity` 为空时不伪造补全。

### 严重度怎么来？三个选项（按成本排序）

| 方案 | 做法 | 成本 | 诚实度 |
|---|---|---|---|
| **S0 人工目测** | 复拍时农户 / 农技员选 0–5 级（配标准图卡） | 0 | 最诚实，先跑通流程 |
| **S1 图像估算** | 病斑分割算面积占比 → 分级 | 要标注 + 训练（中期） | 好 |
| **S2 颜色启发式** | HSV 阈值分割褐色 / 黄色区域占比 | 很低 | **只能当辅助，UI 必须标注「估算值」** |

> ⚠️ **重要诚实点**：当前 `confidence` **不能当严重度用**。置信度是「模型有多确定是什么病」，严重度是「病到了多重」—— 两者完全无关。用置信度画病程曲线属于造假，与本项目「不生成虚构结果」的人格直接冲突。此点必须写进代码注释与 UI 文案。

## 6.6 病程记录长什么样

```
主体：3号棚-第4行-东侧-第2株-下部叶      作物：番茄      首次发现：10-20

 天数   日期     类别           严重度   置信度   干预       判定
 ─────────────────────────────────────────────────────────────────
  D0   10-20   番茄早疫病        2级     0.96    —          初发
  D3   10-23   番茄早疫病        3级     0.94    D1 喷药A    扩展中 ⚠
  D7   10-27   番茄早疫病        3级     0.95    —          停滞
  D14  11-03   番茄早疫病        1级     0.91    —          好转 ✅
  D21  11-10   健康              0级     0.97    —          康复，封存
```

## 6.7 病程能让系统回答的 4 个真问题

当前系统能答：「这张图是什么病？」（农户其实不完全关心）

有了病程，能答：

1. **「我上周打的药管用吗？」** → 干预前后曲线斜率对比。农户付费意愿最强的问题，也是农资店最想知道的（决定复购）。
2. **「这个棚会不会爆发？」** → 全场所有主体的扩展速率排序，快的先处理。
3. **「什么时候复拍？」** → 按当前扩展速率算下次采样时间（3 天还是 7 天），而非固定提醒。
4. **「这片叶子还要不要治？」** → 稳定期 + 低严重度 → 建议观察、止损，不浪费药。

## 6.8 三个真实的技术难点

### 难点 1：怎么知道「这是同一片叶子」？

手机拍两张，角度、光照、距离全不一样。三条路叠加：

- **最可靠：人工绑定**。复拍时 UI 问「这是之前记录的那片叶子吗？」；或扫叶片标签 / 二维码贴纸（成本约 1 分钱一张，农技员场景完全可行）。
- **自动建议**：CLIP / DINOv2 embedding 余弦相似度 + 时间窗（7 天内）+ 同地块同作物 → 给出 top-3 候选供用户点选。
- **辅助信号**：EXIF GPS + 拍摄时间 + 手动 tag。

### 难点 2：类别漂移

D3 识别成早疫病、D7 识别成斑枯病 —— 那不是「病程」，是「模型在抖」。处理：

- 病程曲线**只画同一 crop 的严重度 / 状态**，类别变化单独标「⚠ 类别不一致，建议人工复核」；
- 稳定判定：连续 2 次同类别才认账；
- 本质上又指向 **A1 校准** —— 校准做不好，病程就是噪音放大器。

### 难点 3：采样不等间隔、缺失

D0、D3、D7，然后断两周。处理：

- 曲线必须标注**采样间隔**；
- 扩展速率用**斜率（Δ严重度 / 天）**而不是差值；
- 缺测区间画**虚线**。

## 6.9 两周 MVP（不碰模型）

1. 加 `leaf_subjects` 表 + `subject_id` / `follow_up_seq` / `severity` 字段（迁移兼容现有 SQLite / MySQL，做法同 `detection_predictions`）。
2. 检测页加一步：「新建主体」或「复拍已有主体（选最近 top3）」。
3. 复拍时让用户选 0–5 严重度（配标准图卡）。
4. 新增「**病程**」页：选主体 → 时间轴 + 严重度折线 + 干预竖线 + 扩展速率结论。
5. 手动录入干预事件（一张表单）。

> **完全不重训模型、不改推理代码**。改的只有 DB 三处 + 一个新页面 + 检测流程加一步。

## 6.10 为什么这条比「再刷 0.3% 准确率」值钱

| 对比项 | 单点诊断（现状） | 病程 |
|---|---|---|
| 用户问题 | 「这是什么病」 | 「**在变好还是变坏**」 |
| 竞品覆盖 | 全都在做（Plantix / 识农 / 慧植都一样） | **几乎没人认真做** |
| 数据壁垒 | 无（换个模型就没） | **越用越厚**（时间序列买不到） |
| 用户粘性 | 低（拍完就走） | **高**（不拍就断链，断链就没结论） |
| 与 IP 配合 | 小禾只是讲解员 | 小禾变成「**管床医生**」（跟踪、提醒、复盘） |
| 商业化 | 免费工具 | 可交付报告 / 药效评估凭证 |

> 并且它与已有的 `note`、`image_url`、`candidates` 快照、模型版本 sha **全部兼容** —— 不是推倒重来，是把已经存好的点连成线。
